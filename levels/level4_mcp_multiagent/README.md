# Уровень L4. MCP + мультиагентность — «AI-команда с инструментами»

Две технологии поверх топового харнесса:

1. **MCP (Model Context Protocol)** — открытый стандарт подключения инструментов
   к агентам. Один MCP-сервер работает с любым MCP-клиентом (ZCode, Claude,
   нашим скриптом). У нас: `mcp_testserver.py` — сервер инструментов QA
   (запуск тестов, покрытие, чтение исходников, баг-скан), ноль зависимостей.
2. **Мультиагентность** — конвейер специализированных ролей:
   аналитик (план тестирования) → писатель (код тестов) → критик (запускает,
   меряет покрытие, правит). Каждый артефакт остаётся в проекте для ревью.

## MCP-сервер: как устроен и как проверить

Протокол MCP — JSON-RPC 2.0 поверх stdio: клиент пишет строку-запрос в stdin
сервера, читает строку-ответ из stdout. Смотрите `mcp_testserver.py` — там
~250 строк, включая `initialize`-рукопожатие, `tools/list` и `tools/call`.

Проверка без всяких клиентов:

```bash
python tools/mcp_client.py list
python tools/mcp_client.py call read_source '{"module": "split"}'
python tools/mcp_client.py call run_tests '{"test_file": "results/runs/<run>/test_ordercalc.py"}'
python tools/mcp_client.py call coverage '{"test_file": "results/runs/<run>/test_ordercalc.py"}'
```

Подключение к ZCode (`.zcode/mcp.json` в корне проекта) или аналогам:

```json
{
  "mcpServers": {
    "ordercalc-tests": {
      "command": "python",
      "args": ["levels/level4_mcp_multiagent/mcp_testserver.py"]
    }
  }
}
```

После этого инструменты `run_tests`/`coverage` появляются прямо у вашего агента —
он перестаёт изобретать команды и вызывает стандартные инструменты.

## Мультиагентный конвейер: как сделать

С ключом (скрипт, роли = отдельные вызовы API, критик ходит в MCP-сервер):

```bash
export LLM_API_KEY=... LLM_BASE_URL=... LLM_MODEL=glm-4.6
python levels/level4_mcp_multiagent/multiagent_pipeline.py --out results/runs/l4_multi_glm46
```

В агентной среде (ZCode и т.п.) то же самое делается субагентами: аналитик —
read-only агент с планом на выходе, писатель — генерит файл без запуска,
критик — получает доступ к MCP-инструментам и доводит до зелёного.

Артефакты прогона: `plan.md` (план аналитика), `analyst.txt`/`writer.txt`/
`critic_iter*.txt` (сырые ответы ролей), `test_ordercalc.py`, `meta.json`.

## Почему это мощнее одного агента

- **Специализация**: узкий промпт роли точнее широкого «сделай всё».
- **Разделение власти**: писатель не оценивает сам себя — оценивает критик с
  инструментами. Это структурный контроль качества, а не просьба «проверь себя».
- **Артефакты**: план тестирования пригодится человеку на ревью, даже если код
  тестов перепишут.
- **MCP переиспользуется**: тот же сервер подключается к CI, IDE и любым агентам.

## Плюсы

- Максимальное качество: план → код → безжалостная проверка инструментами.
- Каждый шаг дешёвый и наблюдаемый; легко точечно заменить роль (или модель!).
- MCP-инструменты — общее достояние: один раз написали, везде подключили.
- Масштабируется: роли параллелятся (N писателей по N модулям).

## Минусы

- **Суммарно дороже** одного агента на маленьких задачах (оверхед оркестрации).
- Ошибки композиции: плохой план аналитика портил всё downstream — нужен ревью-шаг.
- Отладка конвейера сложнее, чем одного скрипта (но проще, чем агента-«чёрного ящика»).
- Зависит от качества инструментов: баг в MCP-сервере = баг у всех агентов.

## Когда использовать

Регулярные процессы с высокими требованиями: ночные прогоны генерации тестов,
аудиты безопасности, миграции. Там, где важнее предсказуемость и следы ревью,
а не минимальная цена одной задачи.
